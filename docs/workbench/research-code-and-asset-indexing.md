# Does code/asset indexing help agents? Research findings

Scope: DevGame's four target stacks — **C# (Unity)**, **GDScript (Godot)**, **C++ (Unreal)**, **TypeScript/JS (three.js)**.
Labels: **DOCUMENTED** (cited source), **VERIFIED** (I checked myself — repo grep, GitHub API, direct fetch), **ASSUMPTION** (my inference, not confirmed).

---

## TL;DR

**No, not for code. Yes, but narrowly, for assets — and even there, integrate before building.**

- **Code indexing (semantic/embedding retrieval): skip it.** The strongest evidence — from the teams who tried it, walked it back, and from an independent 2026 academic benchmark built specifically to test this — says embedding-based retrieval underperforms live agentic search (grep/read/glob) for the kind of work a coding agent actually does. This is not a fringe position; it's the position of Claude Code itself and of Cline, and Sourcegraph pulled embeddings out of Cody Enterprise for related reasons.
- **Cheap structural maps (Aider-repo-map-shaped): skip it too, for now, and the reason is language coverage, not principle.** Aider's repo-map has zero GDScript support (VERIFIED) — one of our four target languages gets nothing from the one credible cheap option. Building or maintaining our own would cost real engineering for a benefit nobody has published a clean number for (checked; Aider itself has no isolated repo-map ablation).
- **Full structural indexing (SCIP/Kythe/Glean/Stack Graphs): skip it.** Every candidate has a real gap against our stack — Kythe has no C#/GDScript/TS and is on a skeleton maintenance team, Glean requires standing up a Haskell service for ~10 languages none of which is GDScript, Stack Graphs needs someone to hand-author binding-resolution rules per language and only Python/Java/TS exist today.
- **Asset indexing: the interesting case, and Unity already half-answers it.** Unity ships an **official** Dependency Viewer (`com.unity.search.extensions`) that already does GUID-based uses/used-by queries over scenes, prefabs, and materials — the exact "what breaks if I delete this material" question the brief asks about. It's explicitly a **prototype** with a **manually-refreshed** database, not automation-ready. That's a real, narrow gap. Godot has the equivalent shape (uid://) with a smaller, less mature open-source ecosystem around it, and Unreal/three.js don't have an analogous GUID-graph problem in the same way.
- **Recommendation: (a) do nothing on code — agentic search is sufficient**, and reuse what already exists (LSP servers, which Godot and Unity/C# both already ship, per the "integrate, don't own" doctrine this session is already running on). **(d)-adjacent on assets: don't build a general asset-graph engine; if a real workflow needs "what uses this asset" outside the Unity Editor (e.g., an agent operating headless, or Godot), wrap the existing tools (Pipeline's asset queries, Dependency Viewer's DB, or a thin `.meta`/`.tscn` parser) rather than building a graph database.**

## Part 1 — Does indexing actually help agents?

### The two things people conflate

- **Semantic/embedding retrieval (RAG over a vector DB):** chunk code, embed it, do nearest-neighbor search at query time. Requires a persistent index, a refresh/staleness story, and a similarity metric that's fuzzy by construction.
- **Structural indexing (symbols, call graphs, references):** parse code into an AST/graph and answer exact questions ("who calls this," "where is this defined"). No fuzziness, but needs either a parser per language or a running language server.

The evidence for these two is different, and the "does indexing help" answer is different for each.

### Semantic/embedding retrieval: the trend among agentic coding tools is negative

- **DOCUMENTED** — Claude Code does not index the codebase. Its creator, Boris Cherny, has stated the team tried RAG with a local vector database early on and found agentic search (grep/glob/read on demand) consistently outperformed it. ([vadim.blog](https://vadim.blog/claude-code-no-indexing/), [neurals.ca](https://neurals.ca/tech/claude/agentic-search/))
- **DOCUMENTED** — Cline explicitly rejects RAG/embeddings for three stated reasons: fragmentation (code chunks lose interconnected logic), decay (the index goes stale the moment the codebase changes), and security surface (embeddings duplicate the codebase into a new store). Cline instead follows imports/references sequentially, like a developer reading code. ([cline.bot](https://cline.bot/blog/why-cline-doesnt-index-your-codebase-and-why-thats-a-good-thing))
- **DOCUMENTED** — Sourcegraph removed embeddings from Cody Enterprise, replacing them with Sourcegraph's own (non-vector) search/context system. Stated reasons: the embedding-refresh pipeline is operationally complex, and vector search doesn't scale past ~100k repos. This is a move away from embeddings, but _toward a different index_ (their own code-search backend), not toward pure on-demand grep — worth being precise about. ([sourcegraph.com/blog](https://sourcegraph.com/blog/how-cody-understands-your-codebase))
- **DOCUMENTED, independent** — CORE-Bench (arXiv 2606.11864, 2026), a benchmark built specifically because prior code-retrieval benchmarks (docstring→function matching) don't reflect what an agent actually needs (navigate a real repo, find files/functions, gather context, reject near-duplicate distractors), found a **sharp drop** in representative embedding models' performance when moving from classic code search to this agentic-retrieval-shaped task. This is the closest thing to independent, non-vendor evidence in this research. ([arxiv.org/abs/2606.11864](https://arxiv.org/abs/2606.11864))

**Counter-evidence exists and should not be discarded:**

- **DOCUMENTED (vendor-reported)** — Cursor built a custom embedding model and reports +12.5% agent accuracy from semantic search alone, and up to +23.5% from semantic+grep hybrid vs. grep alone. This is Cursor's own claim, not independently reproduced. Notably, Cursor also hired the engineers behind Claude Code's _agentic_ search in 2025 — i.e., even the pro-embeddings camp is converging toward hybrid, not staying semantic-only. ([cursor.com/blog/semsearch](https://cursor.com/blog/semsearch))
- **DOCUMENTED (vendor-reported)** — Windsurf/Cascade ships a persistent local vector index by default (RAG-first design). Its most recent addition, "Fast Context," pairs the embedding index with custom fast-grep-style models (SWE-grep, SWE-grep-mini) — again, a move toward hybrid rather than a pure semantic bet. ([docs.windsurf.com](https://docs.windsurf.com/context-awareness/remote-indexing))

**Reading the evidence honestly:** the field isn't unanimous, but the specific sub-question "does a prebuilt vector index outperform an agent that can grep/read on demand, for the kind of retrieval an agentic coding loop does" has one independent benchmark (CORE-Bench) and it says no. Every vendor still shipping embeddings is walking toward hybrid, and the tools built by the people with the most public reasoning about _why_ (Anthropic, Cline) rejected pure semantic indexing outright. Nobody in this survey ships semantic-only with no grep fallback.

### Structural/cheap indexing: a real middle ground, but not free, and coverage-gated for us

- **DOCUMENTED** — Aider's repo-map is not an embedding index. It parses files with tree-sitter, builds a directed graph of symbol definitions→references, ranks it with a PageRank-style algorithm, and includes a token-budgeted slice (default 1k tokens) in the prompt, weighted toward files already in the chat/edit context. It requires no external service, no vector DB, and (per the changelog) is cheap enough to regenerate rather than maintain incrementally as a stateful index. ([aider.chat/2023/10/22/repomap.html](https://aider.chat/2023/10/22/repomap.html))
- **Evidence gap, DOCUMENTED (checked directly):** Aider has never published an isolated ablation number for how much the repo-map itself contributes to its benchmark scores — I checked both the original blog post and the full `HISTORY.html` changelog; every repo-map entry is qualitative ("boost ranking for path matches," "watch all files") with no before/after accuracy delta attributable to repo-map alone. The closest thing to "it helps" is that Aider has kept investing in it for years and the maintainer's public reasoning is confident — but that's not a benchmark.
- **VERIFIED (checked via GitHub API directly, not a search summary):** Aider's repo-map language coverage, against our four target languages:
  - C# — **supported** (`csharp-tags.scm` / `c_sharp-tags.scm` exist)
  - C++ — **supported** (`cpp-tags.scm` exists)
  - JavaScript / TypeScript — **supported** (`javascript-tags.scm`, `typescript-tags.scm` exist)
  - **GDScript — not supported.** No `gdscript-tags.scm` exists in either of Aider's two query directories (`tree-sitter-language-pack`, the current one, or the legacy `tree-sitter-languages`).

  This is exactly the failure mode the brief warned about: a tool with real language breadth that goes to zero on the one language (GDScript) unique to our stack. Building or adopting a repo-map-shaped tool today means either shipping it Godot-blind or writing a GDScript tags query ourselves (a real but bounded piece of work — GDScript does have a maintained tree-sitter grammar to build the query against, see Part 2).

### LSP as a third option — not really "indexing" at all

- **DOCUMENTED** — A distinct pattern from both of the above: don't build an index, query the language server that already exists for the IDE experience. LSP servers already maintain a live, always-correct symbol index as a side effect of providing autocomplete/go-to-definition; "indexing" here means standing up a process, not building a database. Emerging protocols (LSAP, `agent-lsp`) exist specifically to expose this to agents as tool calls (`find_references`, `goto_definition`) instead of dumping index contents into context. One cited (vendor-blog, unverified independently) performance claim: find-references via LSP is ~50ms vs. potentially tens of seconds for recursive grep. ([mcpmarket.com/server/lsp-4](https://mcpmarket.com/server/lsp-4), [agent-lsp.com](https://www.agent-lsp.com/))
- This matters unusually much for our stack specifically, because two of our four languages already ship a language server we don't have to build: **Godot ships a built-in GDScript LSP server** (TCP, `127.0.0.1:6005`, runs inside the editor) (DOCUMENTED), and **C# has OmniSharp**, which — while now in maintenance mode as VS Code's default C# backend — is still the standard way to get Unity C# language-server features and works today with a documented config flag (`omnisharp.useModernNet: false`) (DOCUMENTED, with the maintenance-mode caveat noted). TypeScript/JS gets `tsserver`, the best-supported language server that exists, for free. C++/Unreal is the hard case (see Part 2). None of these require us to author or maintain a symbol database — the "integrate, don't own" pattern already applied to Unity/Pipeline this session extends cleanly here.

C++/Unreal is the hard case everywhere on this table, for the same underlying reason: Unreal's reflection macros aren't resolvable from source text alone, only from UHT-generated output, which means any of these tools needs a real Unreal build step to be accurate — that's a cost independent of which tool is chosen.

## Part 3 — Asset indexing (the genuinely novel part)

### The shape of the problem

- **VERIFIED (general knowledge, standard Unity behavior)** — Unity assets get a stable GUID in a `.meta` sidecar file; scenes/prefabs are YAML that reference other assets by that GUID. This makes "what uses this asset" a parseable graph problem from files on disk, without Unity running — matching the brief's framing exactly.
- **DOCUMENTED** — Godot has the same shape with `uid://` references inside `.tscn`/`.tres` text-format resource files, with the same class of failure mode: UID and actual resource can drift apart, producing "references a non-existent resource" errors that are fixed today by re-opening and re-saving the scene in-editor. ([bugnet.io](https://bugnet.io/blog/how-to-fix-godot-scene-uid-mismatch-error-on-open))

### What already exists before we'd build anything

**Unity — two official answers already exist, and this session already has the doctrine for how to treat them:**

1. **VERIFIED (repo read, `unity/README.md`)** — `com.unity.pipeline`, the official Unity package this session already standardized on (deleting 1,633 lines of our own C# on 2026-08-03 in favor of it, per `unity/README.md` and commit `33d6cc4d8`), exposes roughly 130 tools including `get_selection`, `get_console_logs`, `run_tests`, `capture_scene_view`, and editor play/pause/stop control. I did not find documentation confirming a dedicated asset-dependency/find-references tool among Pipeline's ~130 — **flagging as an open question**, not a confirmed gap, since Pipeline's full tool list wasn't enumerable from public docs in this pass.
2. **DOCUMENTED** — Separately, Unity's own `com.unity.search.extensions` package ships a **Dependency Viewer**: select any asset or GameObject, see "Uses" and "Used by" in both directions, get built-in reports for broken/missing/unused assets, with GUID resolution distinguishing "hard" links (real GUID references) from "weak" links (filename-pattern guesses). This is exactly "what breaks if I delete this material." **Important limitation, DOCUMENTED directly from Unity's own wiki**: it is explicitly called a **prototype**, and — critically — **"the Dependency Database is not updated automatically if assets changed on disk."** It also only shows direct (one-hop) dependencies and only GameObjects in the currently-open scene. ([github.com/.../dependency-viewer wiki](https://github.com/Unity-Technologies/com.unity.search.extensions/wiki/dependency-viewer))

That second point is the real finding of Part 3: **Unity has already built the exact tool the brief is asking about, and it has a real, documented gap** — no auto-refresh, one-hop only, prototype status. If an agent needs "what uses this asset, and I need to trust the answer without a human re-opening the editor to refresh a database first," that's a legitimate present-day gap even after "integrate, don't own."

3. **DOCUMENTED (community, not official)** — Several open-source Unity dependency-graph tools exist beyond Unity's own (`Unity-AssetDependencyGraph`, `AlexeyPerov/Unity-Asset-Inspector`, `AlexeyPerov/Unity-Dependencies-Hunter` for unreferenced-asset detection, `NeustonIO/AssetDependencyGraph` for a queryable relationship graph, and at least one purpose-built "index Unity assets into a SQLite reference graph, serve via CLI/MCP/web viewer" project surfaced in this research). None of these are Unity-official; all solve some slice of the same GUID-graph problem community tools have re-solved repeatedly, which is itself a signal that Unity's own first-party answer (Dependency Viewer) doesn't fully satisfy the need.

**Godot:** DOCUMENTED — a community "Scene Dependency Viewer" addon exists (Godot Asset Store) that scans the whole project, resolves UIDs, and surfaces broken references and unused assets — the same shape as Unity's Dependency Viewer, but third-party rather than engine-official, and Godot has no equivalent to Pipeline (no official local-API automation package at all — confirmed by this repo's own `unity/README.md`, which states Godot and Unreal "still use our Editor Presence publishers, because neither engine has an official equivalent").

**Unreal / three.js:** no evidence surfaced in this research of an equivalent GUID/UID asset-reference-graph problem in the same shape. Unreal's asset references go through its own Redirector/soft-reference system inside the `.uasset` binary format (not a readable text sidecar like `.meta`/`.tscn`), which is a materially harder parsing problem and out of scope for what this research turned up evidence on either way. three.js (plain TS/JS) doesn't have an engine-level asset-GUID system at all — that problem doesn't exist for it in the same form.

## Part 4 — Recommendation

**On code: (a) do nothing beyond what already exists.** Agentic grep/read/glob is the evidenced-strong default, matching what Claude Code and Cline themselves ship, and reinforced by CORE-Bench's independent finding that embeddings underperform specifically on agentic-shaped retrieval. Where an agent needs exact structural answers ("who calls this," "go to definition"), **prefer wiring up the language servers that already exist for Godot (built-in) and C#/Unity (OmniSharp) rather than building or adopting a new index** — this is the same "integrate, don't own" call this session already made for Unity Play/Stop and selection, applied to the same problem shape. C++/Unreal is the one language where nothing is free: any structural tool (clangd, SCIP, tree-sitter) needs a real `UnrealBuildTool -mode=GenerateClangDatabase` pass first, and even then the reflection macros (UCLASS/UPROPERTY/GENERATED_BODY) are a documented pain point industry-wide, not something this research found a clean answer for.

**On assets: narrow, deferred (d)-shaped.** Don't build a general asset-graph engine now. The Unity half of the problem already has an official (if limited) answer — Dependency Viewer plus whatever Pipeline itself exposes (open question, worth a direct check against Pipeline's actual tool list before deciding anything). The real, evidenced gap is Dependency Viewer's manual-refresh requirement, not the absence of a tool. If an agent workflow needs a live, always-fresh "what uses this asset" answer, the cheapest fix is very likely a thin wrapper — either drive Dependency Viewer's refresh via Pipeline's `eval`/`eval_file` capability (already available, per `unity/README.md`) rather than parsing `.meta`/YAML ourselves, or write a narrow-scope `.meta`/`.tscn` GUID-graph parser only for the specific query an agent actually needs, not a general graph database. Godot has no official equivalent, so if an agent workflow needs this for Godot specifically, that's the one place building something small ourselves is defensible — scoped to "resolve `uid://` references in `.tscn`/`.tres` files," which is a bounded, well-specified parsing task, not an open-ended indexing project.

**What would change this answer:**

- If Pipeline's ~130 tools already include a live, auto-refreshing asset-reference query (the one open question this research didn't resolve) — that closes even the narrow Unity gap and moves the whole asset-indexing recommendation to pure (a).
- If a workflow emerges where agents are doing large, cross-file refactors inside a single language repeatedly (e.g., heavy TypeScript/three.js work) and grep-based context assembly is visibly costing turns/tokens — that's the specific shape CORE-Bench and Cursor's own numbers suggest hybrid grep+something helps, and Aider's repo-map (once someone writes the missing GDScript query file) becomes worth a cheap trial, scoped to one language, not a platform investment.
- If Unreal C++ work becomes a significant fraction of agent activity and the macro-blindness of naive parsing starts causing visibly wrong answers — that's the trigger to invest in the `GenerateClangDatabase` + clangd pipeline specifically, not a general indexing platform.
